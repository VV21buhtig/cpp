webgpuelectronsdh_engine — ЦЕЛЬ + ОГРАНИЧЕНИЯ v0.1
Принцип: сначала режем, потом расширяем. Расширять проще, чем урезать.

=== 1. ЦЕЛЬ ===
Одно C11-ядро (sdf_core + renderer на webgpu.h), которое едет везде:
  native (Linux/Win: Dawn + GLFW, while-цикл)
  web (Emscripten + emdawnwebgpu + -sUSE_GLFW=3, emscripten_set_main_loop / ASYNCIFY)
  Electron — только оболочка, грузит emcc-сборку (HTML+WASM) как есть.
Сцена — SDF в WGSL (map() как в renderer.js-прототипе). C только описывает
сцену и шлет камеру/время/параметры юниформами. Потом — ручной перевод
горячих мест в asm ради памяти (только после стабильного C на WebGPU).

=== 2. КАК РАБОТАЕТ SDF (коротко) ===
f(p) = дистанция со знаком до поверхности. + снаружи, - внутри, 0 = поверхность.
Рендер = sphere tracing: идем по лучу шагами h = map(p), ближайший хит не ближе h,
поэтому безопасно. Хит если h < eps*t (eps растет с дистанцией).
CSG: union = min(a,b), subtract = max(a,-b), intersect = max(a,b).
smin(a,b,k) = гладкое смешивание (blob), но ЛОМАЕТ bound (не 1-Липшиц) -> шаг надо
домножать на 0.7-0.8 иначе проскоки. У нас в прототипе k=0.6 + полный шаг — риск.
Нормаль = градиент поля (тетраэдр: 4 вычисления map). Тени = второй марш к солнцу.
Туман = exp по дистанции. Небо = градиент + диск солнца.
Формулы примитивов — только iq, ничего не выдумывать.

=== 3. ОГРАНИЧЕНИЯ v0.1 (заморозка) ===
Геометрия: plane + 2 сферы (smin) + 1 box + 1 вычитаемая сфера-дырка. ВСЕ.
  Нет: repeat/tiling, фракталы, displacement noise, L-системы, биомы.
Марш: max 100 шагов, maxT=60, 24 шага тени. Лимиты константы, не крутить в UI.
Материалы: 3 плоских цвета по id (земля/блоб/бокс). Нет текстур, нет PBR.
Свет: 1 солнце (dir + цвет), ambient по n.y, soft shadow. Нет: точечных, bloom, HDR.
Камера: orbit (yaw/pitch/dist/target). Нет WASD/free-fly в v0.1 (добавим в v0.2).
Разрешение: фиксированный fullscreen-треугольник, 1 draw(3) за кадр, 1 UBO 48-64Б.
  dummy-текстура 1x1 только чтобы биндинг был валиден, НЕ использовать для res.
Пост: только fog + sky mix. Нет: exposure/Uchimura/TAA (это v0.3 как в vulcan).
Память: 0 malloc в кадре. UBO-зеркало на CPU + writeBuffer, ring 2-3 кадра в C-версии.
Платформа: только Chrome/Edge 113+ / Electron 28+ (WebGPU). Firefox/Safari — не цель.
Ассеты: ноль загрузок, ноль preload. Шейдер — инлайн-строка, без сборщиков.

=== 4. ПАМЯТЬ (почему потом asm) ===
Сейчас JS: GC, 1 UBO + 1 writeBuffer/кадр — ок для прототипа.
В C: арены под кадр (линейный аллокатор, сброс в конце кадра), пул командных
буферов, UBO mirror + memcpy (как vulcan-render). Ноль аллокаций в лупе — религия.
В asm (ПОТОМ): только доказанные горячие места: SDF-eval на CPU (если будет),
математика камеры, arena alloc. WGSL на GPU в asm не переводится. Сначала профайлинг.

=== 7. ДВИЖОК+РЕДАКТОР (решение, ветка engine) ===
Не игра. Пять ядер, у каждого: рендер пустой сцены + базовые инструменты.
Потом редактор: подключение ядер по API, выбор при создании проекта.
Игровых механик внутри движка нет — только API. Механики живут снаружи.
Язык: C11 везде для нового. C++ только где незаменим (живущий vulcan, позже UI редактора если припрёт).

Ядра по порядку:
1. webgpu-лучи (этот движок): DDA-воксели + небо LUT + стриминг. Вытащить ядро
   (init/frame/submit, мир как данные), механики (полёт/guard/меню/часы) наружу.
2. opengl-растр (ветка noflood): ядро + мешинг квадов + тени-карты + CVar/гамма.
3. vulkan-растр (vulcan-render): флагман, ядро уже почти отделено (main 74 строки).
4. sdf-марш: аналитика (лестница 0-4 как зародыш), позже.
5. 2D (вектор/пиксель): после 3D-ядер.

Редактор: один API поверхности init/frame/submit под каждое ядро,
пустая сцена + инструменты, выбор ядра при создании проекта.
